# Chapter 13. How the book checks itself

A book built from a growing dataset can go wrong in a way a printed book cannot: a sentence true on the day it was written can become false when someone adds a game. The build fills in every number in the earlier chapters and tests {{stat:n_book_assertions}} claims about how those numbers rank, compare, and group against the data, and anyone can run those checks or add to the data. The checks confirm that the text matches the data; whether the data is right about the games is left to reviewers.

On 25 October 2026 an AI agent catalogued three mobile management games, Pocket City, Fallout Shelter, and Game Dev Story, and ran the dataset's checks before opening a pull request. The data passed. The paper did not. A sentence in the paper's section on white space, the pairs of common mechanics that almost never meet, had stopped being true, and the build refused to finish.

The sentence named building placement and embodied skill control, real-time motor skill such as hand-flying a plane or driving a car, as one of the most promising empty pairs. Behind it sat an assertion that the pair ranks in the top ten of the white-space table. The new games did not touch either mechanic. The trouble was the table's entry rule: it admitted mechanics used by at least 8 percent of the catalog, and embodied skill control was used by exactly {{derived:embodied-skill-control.prevalence}} games, sitting on the bar.{{assert:derived.embodied-skill-control.prevalence == whitespace_min_games}} Three more games without it pushed it under 8 percent, it dropped out of the table, and the paper's sentence lost its footing even though no finding had changed.

The build caught it, and also showed a weakness in how it reported the problem. The error said "unknown reference", which pointed at a typo rather than at the cause. The fix, recorded in the project's fifth decision record, changed two things. The table now admits mechanics used by at least a fixed number of games, {{stat:whitespace_min_games}}, which was 8 percent of the catalog when it was fixed, so adding games can no longer push a mechanic out.{{assert:whitespace_min_games >= 10}} And an assertion about a row that has left a table now fails with a message saying so. Before the change was accepted, the same assertions were run against scratch copies of the catalog with the three games added and with up to twenty duplicated games on top; under the old rule the three games alone broke one, and under the new rule none broke.

It is a small example of how a dataset, a paper, and a book built from it stay true while people and agents keep adding to them.

## Everything is a build

The dataset is a folder of plain-text records: one file per game, mechanic, technique, opportunity, and source, plus a log of every run that changed anything. There are {{count:game}} game files, {{count:mechanic}} mechanics, {{count:technique}} techniques, {{count:opportunity}} opportunities, and {{count:source}} sources. Everything else is computed from those files on every build: the paper, the website, the wiki pages, the tables and figures, and this book. Nothing derived is stored. The prevalence of a mechanic, the earliest game that uses it, a game's cluster, an opportunity's priority: each is recomputed from the records every time, because a stored copy would drift from the data it was copied from.

{{viz:pipeline}}

Prose is the hard part, because sentences interpret numbers. Two rules handle it. Every number about the dataset in this book is a placeholder that the build fills in, so no count is typed by hand; a literal count next to a word like "games" or "mechanics" fails the build. And a sentence that ranks, compares, or groups numbers carries an assertion that the build evaluates; {{stat:n_book_sentences_asserted}} of the book's {{stat:n_book_sentences}} sentences carry one or more. When chapter 1 says that four of the five most common mechanics model nothing in the world and that production chains come seventh, the build checks the five ranks and the seventh. When the data stops supporting the sentence, the build fails until someone rewrites it.

The build is also deterministic. The same files produce byte-identical output, and the project's checks prove it on every change by building twice under different settings of Python's hash randomization and comparing the results. That is what lets an edition of this book name the exact version of the dataset it came from.

## One file per record

The architecture was set down in the project's first decision record, which names four usual sources of drift in a shared dataset: the same fact stored in two places, open-ended fields and tags, prose that restates numbers, and contributors who each reinterpret a category. Every record is its own YAML file, so a merge conflict stays inside one game or one mechanic. Schemas are closed, and their annotations say which fields take a closed vocabulary, which point to another record, and which are scored on an anchored scale; the validator and the build read those annotations, so a new field that points to another record appears in the graph, the wiki, and the tables without new code. Every link between records has one owner, and the reverse link is computed. Changing a vocabulary, a rubric, a schema, or a rule needs a decision record, and the documentation of the rules is generated from the code that enforces them.

The record also lists what was rejected. One large YAML or CSV file would be simpler, but every edit would conflict and partial validation would be hard. A graph database would answer queries better and make changes harder to review, so the build exports a database for queries instead. Free tags with periodic cleanup were rejected because they drift. The cost was accepted on purpose: a contributor cannot add a tag casually and has to file a proposal, which slows the growth of the taxonomy.

## Eleven ways to drift

The second decision record came from a test designed to break the first. An independent agent, given only the repository, followed the agent instructions (AGENTS.md) to add a game and then tried eleven ways to introduce drift. Most were caught. The ones that were not became rules. Any second run could mark a record verified. A literal count slipped past the lint when a word sat between the number and its noun, or when it was written as a percentage. Interpretive prose had no check against the data. Summaries could carry em dashes and hype. A run of any kind could create new mechanics. The documented order of the final checks could never succeed after an edit.

The fixes gave every run a kind, so that only taxonomy and bootstrap runs create mechanics and only verification runs can justify a verified status. The count lint now catches a number up to one word before a dataset noun and exempts sentences that cite an outside source. The assertion syntax this book uses in every chapter came from the same record. And the contract itself, meaning the vocabularies, schemas, scripts, and agent instructions, went under maintainer review, because a validator can enforce a contract but cannot judge a change to it.

## Failures that shaped the rules

Most of the rules exist because something went wrong once.

The first version of the catalog was built by agents working in parallel, each cataloguing a slice of games. An independent reviewer, reading the paper against the data, found that they had tagged each game's distinctive mechanics and skipped the ubiquitous ones: pause controls, building placement, tech trees. Prevalence, clusters, and white space had all been computed on incomplete decompositions, and chapter 1's finding that most of the commonest parts of a simulation game simulate nothing could not have been seen in that data. The gaps were filled, clustering was changed to weight each mechanic by how rare it is, so that two games sharing a pause button count for less than two games sharing a storyteller, and the analysis was redone.

The same review found prose that contradicted the records. The paper called some techniques determinism-breaking that the data scored as mitigable. The fix was a new kind of assertion that reads a stored field directly, so the sentence in chapter 11 that calls a technique mitigable is checked against that technique's record.{{assert:field.monte-carlo-tree-search.determinism_impact == mitigable}}

A later review found that the cluster findings were fragile. The reviewer removed one game at a time and re-ran the analysis; several sentences about which games belong together failed, because the subsamples used to test the clusters' stability were drawn by position and changed whenever the catalog did. Each game's membership in each of the {{stat:cluster_subsamples}} subsamples is now fixed by a hash of its id. A sentence may say two games belong together only if they share a cluster in at least {{stat:cocluster_together_pct}} percent of subsamples, and the assertions were re-tested with every single game removed in turn.

The number of clusters has its own rule. The build picks the smallest number of clusters whose stability across subsamples reaches a stated threshold, and the configuration fixes that number so that each new game does not reshuffle every cluster. When the data moves far enough that the rule would pick another number, the validator warns, and the number is chosen again by the rule in a maintenance run, which is how it came to be {{stat:cluster_k}}.{{assert:cluster_k == cluster_rule_k}}{{assert:cluster_k_drift == 0}} Chapter 4 says what this means for the families it describes: the curve is flat, neighbouring choices are about as defensible, and only groupings that survive resampling are asserted.

## A field and a mechanic that disagreed

The fourth decision record, written before outside contributors were invited, found record text that contradicted the data. Two opportunity theses called the tech tree the most common mechanic in the catalog and production chains the most used rule-system, when they ranked third and fifth at the time. Report prose was pinned by assertions; record text was not. Records may now carry assertions of their own, and a record whose text states a dataset finding, caught by phrases such as "in the catalog" or "most-used", must carry at least one.

The same review found two mechanics that duplicated fields. Pause and speed control duplicated each game's time model, and mod support duplicated its modding field, and the pairs disagreed: a few games that could be paused lacked the pause mechanic, and nearly thirty games with scripting or total-conversion modding lacked mod support, RimWorld among them, although the mechanic's own definition cited RimWorld. Vocabulary terms can now require or allow a mechanic, and the validator checks every game against them. When the data was migrated, mod support rose to the third most used mechanic in the catalog. The migration also reshaped the head of the distribution: production chains, fifth when the review began, fell to sixth behind mod support. A later pass checked the book's claims that no game, or only one, combines two mechanics against the games themselves, and found city builders, tycoons, and business games that keep a treasury without the tag. Adding it moved the treasury to fourth and production chains to seventh. A follow-up pass, reading each game's own patch notes, blogs, and manuals, found the same gap in the Anno games and in grand strategy, and the treasury rose to third, ahead of mod support, the order chapter 1 reports.{{assert:derived.budget-treasury.prevalence_rank == 3}}{{assert:derived.modding-api.prevalence_rank == 4}}{{assert:derived.production-chain.prevalence_rank == 7}}

Until the same review, every projection the build makes was committed to the repository and checked byte for byte. Every pull request that changed data carried thousands of regenerated lines, and any two pull requests open at once conflicted. Projections are now built and never committed. The check builds them in memory and compares only the generated blocks that change with the contract, a vocabulary, or a rule, and the website is built and published by a workflow from the same sources.

## Four pilots

The fifth decision record followed four pilots. Before outside contributors were invited, four agents each took one task end to end, working only from the written briefs, each in its own copy of the repository: archive twenty-five sources, add verbatim quotes to eight records, add store identifiers to ten games, and catalogue the three games that opened this chapter. Each kept a log of where it got stuck.

Some checks had passed without checking anything. The source checker printed only warnings when every fetch failed, which looked like a pass; it now prints that nothing was checked. The local check before a pull request fell back to the machine's user name when no GitHub handle was configured, which skipped the operator check without saying so; it now refuses to run. The scope check skipped run files when a pull request changed no records; it now checks them, and rejects a pull request that adds a run and changes nothing else.

The briefs had gaps the agents found by falling into them: which archived snapshot to use, which store edition counts for a game first released free or on another platform, what to do with a claim that overreaches or states an absence, and whether adding a quote counts as verification. It does not; quoting runs as maintenance, because it needs no independence and changes no status. The agents' web tools could not reach the web archive, Wikidata, or IGDB from their sandbox, so the briefs now say which tasks suit people, or agents running with full network access. In the catalog pilot, the extracted page text gained a space where an inline tag met punctuation, so four correct quotes failed; the new failure message showed the cause at once.

The catalog pilot also fixed the threshold of {{stat:whitespace_min_games}} games at which a mechanic counts as common in the vacant-lot table, and the decision record sets the review chapter 9 asks for when the catalog passes about two hundred and fifty games.{{assert:whitespace_min_games == 14}}

## Status is a claim about evidence

Every record has a status, and the status is a claim about its evidence. `asserted` means the record has not been promoted on the strength of a source; most asserted records cite nothing, and {{stat:n_asserted_citing}} already cite a source in a claim. `sourced` means the record cites sources. `verified` means someone other than its creator checked it against a primary source. Today {{stat:n_sourced_or_verified}} records are sourced or verified and {{stat:n_asserted}} are asserted, among them every opportunity, since an opportunity is an argument: the sources it cites document prior art, the work its novelty is measured against, not the claim that the design would work.{{assert:n_opportunity_asserted == n_opportunity}}{{assert:n_opportunity_no_sources == 0}}

A claim may carry a verbatim quote from its source, and the project's continuous checks fetch the source and look for the quote whenever the record changes. The first time this ran on agent-written records, it found 26 of 32 quotes, warned on five pages it could not reach or could read only as an abstract, and failed one. The failed quote was on the page; the checker had been served a variant of it. The checker now fetches a page a second time before failing a quote, and a failure says how far the quote matched and what the page had instead.

Disagreement is recorded rather than settled by overwriting. [[utopia|Utopia]], the Intellivision city builder, has two release years in its sources: Wikipedia dates it to 1982 and Guinness World Records to 1981 [@src-wikipedia-utopia; @src-guinness-2026-first-city-building-game]. The record keeps both, marks itself `contested`, and states which year it uses and why. It is the only contested record so far.{{assert:n_contested == 1}}

Verification waits on other people, because of the independence rule. A verification must come from a run with a different operator from the run that created the record and, when both runs are agents, a different model. I built the dataset by directing AI agents, and for its first week every run had one operator, me. The first outside contributor's verification run, with an agent on a different model from the one that wrote the records, made the first {{stat:n_verified}} records `verified`.{{assert:n_runs_verification >= 2}}{{assert:n_verified > 0}} The run log now holds {{stat:n_runs}} runs, all by agents, from {{stat:n_run_operators}} operators.{{assert:n_runs_agent == n_runs}}{{assert:n_run_operators >= 3}}

The same reasoning covers scores. The original mechanic scores, from legibility to AI leverage, were one model's reading of written anchor text. An independent rater has now added a second reading for part of the vocabulary. Each new rater must first score a calibration set of {{stat:n_calibration_mechanics}} mechanics and agree with its reference scores, within one point, on at least eight in ten. The set was frozen and chosen across the mechanic families, greedily, to cover as many combinations of scale and anchor as possible, so changing one of its scores is a reviewed change. Its reference scores are public. The gate therefore shows that a rater reads the anchors the way the set does; it cannot show that the rater scored blind or did not rescore until it passed, and the scoring tool reports only overall agreement to make rescoring less informative. Independent second ratings now cover {{stat:n_scores_independently_rated}} of the {{stat:n_mechanic_scores}} mechanic scores.{{assert:n_scores_independently_rated > 0}} The build reports agreement by scale, and fields with multiple ratings store their lower median. Findings about the full vocabulary still rely largely on the original rater.

## Runs and their limits

Every change belongs to a run: a record that says who operated it, whether a person or an agent did the work, which model and which software ran it, what the run was for, and what it did, including what failed. Runs are append-only. A record names the run that created it and every run that later reviewed it, and the history of any fact can be reconstructed from the run log and the version history. A pull request carries exactly one run, changes at most a bounded number of records, never deletes a merged record, and is signed off by its operator.

Runs so far fall on {{stat:n_run_days}} days, the first on {{stat:first_run_date_long}}. It holds {{stat:n_runs_catalog}} catalog runs, {{stat:n_runs_taxonomy}} taxonomy runs, {{stat:n_runs_maintenance}} maintenance runs, {{stat:n_runs_technique}} technique runs, {{stat:n_runs_synthesis}} synthesis runs, {{stat:n_runs_bootstrap}} bootstrap run, and {{stat:n_runs_verification}} verification runs.{{assert:n_runs_verification >= 2}}{{assert:n_runs_bootstrap == 1}} These are the kinds the rules above key on.

The run log holds what each run declares about itself. The checks bind a run's operator to the account that opened the pull request, but an agent's model is self-declared, and the independence rule cannot catch a false entry. The quote check confirms that a quote appears on its source page; it cannot confirm that the quote supports the claim. The assertions confirm that a sentence matches the data; they say nothing about whether the data matches the world, or whether the reading a sentence gives of the data is the right one. The catalog favours games documented in English, as the preface says, and no check can see the games that are missing. The checks catch drift, contradiction, and counts typed by hand; whether a sourced claim is right about the world is still a reviewer's call.

## How to contribute

The dataset is open, and the same rules apply to everyone who extends it, people and agents alike. The repository's task list holds bounded jobs, each with a brief: cataloguing a game, adding verbatim quotes to claims, archiving sources, adding store ids, verifying records, rating scores, and resolving predictions. A contributor comments on a task issue to claim it, does the work in one run, and opens a pull request that the checks review before a person does.

The three jobs that only outsiders can do are the ones that would change this book most. Verifying records moves them to `verified`. Rating scores turns one model's readings into measured agreement. Resolving predictions fills in the scoreboard of chapter 12. Each needs an operator other than the dataset's maintainer, which is why the guide for invited contributors starts with them. A contributor who disagrees with a record, a rule, or another contributor opens a dispute, a data-error report, or a proposal, and the disagreement goes into the record, as Utopia's release year did.

The first outside contributions failed two sentences in this book, the ones asserting that no record was verified and that every run had one operator, and this chapter now carries their rewrites.{{assert:n_run_operators >= 2}}{{assert:n_verified > 0}} The first independent ratings then failed the sentences in chapters 5 and 13 asserting that no score had a second rating, and those carry rewrites too.{{assert:n_scores_independently_rated > 0}} The sentence asserting that every prediction is open still holds, with an assertion that the first resolved prediction will fail.{{assert:n_predictions_open == n_predictions}}
