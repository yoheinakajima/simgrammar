## 11. Predictions and research agenda

Every opportunity carries a falsifiable prediction with a resolve-by date and criteria a stranger could check. The first resolves on {{stat:first_prediction_resolves_long}}. Because predictions are data, resolving one is a pull request: a verification run by a different operator (and model, for agents) adds a `resolution` with its outcome and evidence to the prediction (`tasks/resolve-prediction.md`), and the table, report, and site update. {{stat:n_predictions_open}} of {{stat:n_predictions}} predictions are open.

**What a resolution would show.** A prediction tests where a technique lands only if its criteria require that technique. Every prediction's criteria therefore end with a sentence that names the technique class that counts and calls the prediction one of two kinds, and the build counts them. A technique test is one whose criteria only the technique class the opportunity applies can meet: a language model that ranks authored events ([[drama-aware-storyteller]]), or a trained policy that drives a physics character ([[neural-npc-motion]]). The class need not be learned; [[qd-scenario-libraries]] requires quality-diversity search, an evolutionary method, because that is the technique it applies. A feature test is one whose criteria classical, symbolic, or operations-research methods can also meet, and its sentence names such a method. {{stat:n_predictions_technique_test}} of the {{stat:n_predictions}} predictions are technique tests and {{stat:n_predictions_feature_test}} are feature tests.{{assert:n_predictions_unclassified == 0}}{{assert:derived.drama-aware-storyteller.prediction_test == technique}}{{assert:derived.neural-npc-motion.prediction_test == technique}}{{assert:derived.qd-scenario-libraries.prediction_test == technique}} Only the technique tests score where techniques land. A confirmed feature test shows that the feature shipped, and which technique built it only where the evidence says so; several feature-test sentences name that evidence, such as release notes saying that a language model writes the answers.

The three legibility tools are feature tests for two different reasons. [[branch-preview-forecasts]] and [[bottleneck-explainer]] need no language and no learned component: forked runs of the game's own simulation under different random draws, or perturbations of it, meet their criteria, and their sentences name classical Monte Carlo runs and sensitivity analysis as counting.{{assert:derived.branch-preview-forecasts.prediction_test == feature}}{{assert:derived.bottleneck-explainer.prediction_test == feature}} [[causal-why-query]] needs free-text questions answered from the player's save state. A language model is the likelier way to build that, but a parser for a fixed grammar of questions over a cause-linked event log, answering from templates, also meets the criteria as written, so the prediction stays a feature test, and its sentence says that a confirmation shows a language model landed only if the release notes say one writes the answers.{{assert:derived.causal-why-query.prediction_test == feature}}

**Spread or arrival.** For {{stat:n_predictions_diffusion}} of the {{stat:n_predictions}} predictions, the prior-art search of §9.1 found a game, official release, or mod that already does the feature or a narrower form, so a confirmation would show the feature spreading; only {{stat:n_predictions_new_capability}} would show a capability arriving for the first time, and all {{stat:n_predictions_first_year}} predictions due in {{stat:first_prediction_year}} are of the first kind.{{assert:n_predictions_first_year_diffusion == n_predictions_first_year}} Each prior-art entry names those earlier titles, and a confirmation that comes from one of them, through a patch or an expansion, shows that title extending its own feature.

**Generic diffusion.** A prediction of the form "a game will ship X" can come true through general adoption of AI without the mechanism its opportunity proposes. General adoption is common and mostly shallow. A little under a fifth of the games released on Steam in 2025, counted in July, disclosed generative AI [@src-totallyhuman-2025-steam-genai-count], and among the 45 disclosing titles that a rough revenue estimate puts at a million dollars or more, about half cited in-game art and under 5 percent cited runtime generative systems [@src-totallyhuman-2025-steam-ai-revenue]. These figures are loose context, not a baseline: they come from a vendor's tally of self-reported disclosures on one store, mostly about pre-generated art, and they count something other than the runtime features predicted here. Some predictions forecast the spread of a feature that already exists, as [[generative-decoration-catalogs]] does when it excludes [[inzoi]], and most are feature tests, so a confirmation can come from methods that owe nothing to the catalogued techniques.{{assert:n_predictions_feature_test > n_predictions_technique_test}} Each prediction therefore has a baseline, set before any resolved and kept in `report/predictions.yaml`: the reference class a resolver counts, named by Steam tags and the size bar of the criteria; the generic version of the event, the same event arriving through general adoption of AI or through classical methods; and what a confirmation's evidence must show to count for the thesis.{{assert:n_prediction_baselines == n_predictions}} For [[causal-why-query]] the generic version is a chatbot that answers from a wiki or general knowledge, and only answers drawn from the player's own save count for the thesis. The criteria alone decide the outcome. The baseline decides what a confirmation shows, and a confirmation without the thesis evidence is recorded as generic diffusion. The build fails when a live prediction has no baseline, when a baseline names an opportunity that is missing or deprecated, or when a reference class names a review count that the criteria do not state.

**Size bars.** {{stat:n_predictions_amended}} criteria had no size bar: those of [[ai-liquidity-in-player-markets]], [[calibrated-serious-sims]], and [[participatory-planning-sandboxes]].{{assert:n_predictions_amended == 3}} On {{stat:prediction_amendment_date_long}}, before any prediction had resolved, each gained one.{{assert:n_predictions_resolved_by_amendment == 0}} The market prediction now needs a game with at least 1,000 Steam user reviews or a console release, the serious-simulation prediction the same review count or at least 100 players reported in a study, and the planning prediction a consultation in a city of at least 100,000 residents. Each amendment only adds a condition, so anything that meets the amended criteria met the original ones. A raised bar can turn a hit into a miss and never a miss into a hit, and since no prediction had resolved, it moved no outcome. All criteria but the planning prediction's now name a Steam review count.{{assert:n_predictions_without_review_bar == 1}} The other bars were left as written, though a console release can stand in for the review count in {{stat:n_predictions_console_alternative}} predictions. That clause sets no audience size, so a minor console title could meet a criterion the review bar was meant to close; amending those criteria to a console release with a public sales or player figure comparable to the review bar is open work (§11.1). The review bars themselves, which differ by prediction, were set by the rater who wrote the predictions, after the predictions were published and without a written rule, so they are among the baselines §11.1 asks a second reader to check. Every release of this paper is archived on Zenodo with its dataset hash, so the criteria and baselines of each version sit in a dated, hashed record made before any prediction resolved. No probabilities were added. One attached now would come from the rater who wrote the prediction, another self-generated judgment; the base rates above are counts, not forecasts. When a prediction comes due, its resolver counts the reference class again: how many of its titles shipped the feature in the window and, of those on Steam, how many disclose generative AI, which is the generic-diffusion rate on that day (`tasks/resolve-prediction.md`).

**A rule for the set.** Single predictions cannot score the thesis of §9.2, that learned models land around a symbolic core through validated, logged interfaces, so the set gets a rule, fixed in this version before any prediction resolves.{{assert:n_predictions_open == n_predictions}} Only technique tests confirmed with the thesis evidence of their baselines count toward it, since a feature test or a generic-diffusion confirmation can come true without the mechanism. The thesis is supported if at least half of the {{stat:n_predictions_technique_test}} technique tests are confirmed that way by their dates, and weakened if fewer than a quarter are; between the two, the set does not decide. The lower mark sits near what deployments before the window already showed: {{stat:n_predictions_technique_test_in_class}} technique-test classes held a counting deployment before the window opened, and generic diffusion alone confirms none, because each needs its own technique class. One outcome counts against the thesis whatever the tally: a confirmed prediction whose evidence shows a learned model writing authoritative simulation state with no validator or log, the design the thesis expects not to ship. Probabilities attached to each prediction by independent raters before it comes due would let the set be scored for calibration as well (§11.1).

The evidence is also asymmetric, as the note under the prediction table says: a refutation can reflect cost, schedules, or reception rather than a wrong thesis, and a confirmation supports the thesis only as far as the criteria and the baseline require the opportunity's own mechanism. The dates are the rater's judgment, not derived from studio lead times. The {{stat:n_predictions_first_date}} predictions due first leave little more than a year from when they were written, so they test mainly patches, expansions, and games already in production.{{assert:n_predictions_first_date >= 5}}

Predictions that depend on how a game is built inside, such as model calls only on salient events ([[salience-gated-llm-agents]]), a learned weather emulator ([[learned-weather-layer]]), or a mean-field crowd model ([[mean-field-crowds]]), name public evidence that counts: developer documentation, postmortems, patch notes, or behavior modders have verified. Outsiders often cannot see architecture, so these predictions risk false negatives (the feature shipped, but no public source says how it works) and false positives (marketing copy that overstates it, accepted by a verifier at face value). The outcome vocabulary has no term for the first case. *Ambiguous* needs evidence that a criterion cannot be checked as written, and *refuted* needs a criterion shown unmet, so a prediction that no public evidence can decide either way would be forced into one of them. An *undetermined* outcome, distinct from refuted, needs a vocabulary change by ADR; until one exists, a verifier facing that case should record it as ambiguous and say in the note that no public evidence exists.

### 11.1 Agenda

1. **Instrument a simulation for explanation.** Build the event log with cause links that why-queries, branch previews, and chronicles all need, and measure explanation faithfulness against human audit.
2. **Measure legibility in players, not only in rubrics.** The legibility and emergence scores here are judgments by a single model rater; a shared protocol for measuring how quickly players form correct causal models would let designers compare mechanics empirically.
3. **Connect techniques to the economic core.** Resource and production mechanics are the most used family in the catalog and, per mechanic, among the least reached by recorded technique edges, and logistics mechanics fare no better (§8.2).{{assert:most_used_family == Resources & production}}{{assert:rank.family-mean-exposure.resources-production >= 16}}{{assert:rank.family-mean-exposure.logistics-networks >= 16}} Balance search, recipe generation, and bottleneck explanation are tractable first steps.
4. **Separate authoritative and generated layers.** Develop and benchmark architectures where learned models render, narrate, or propose, and symbolic state decides.
5. **Extend the dataset.** Add mobile and non-English simulation traditions, score mechanics with a second, calibrated rater on a sample of about {{stat:n_alpha_sample_max_best}} mechanics stratified by family (`calibration/`, `tasks/rate-scores.md`, §5.6), resolve the verification queue, and record design tensions with evidence from postmortems.
6. **Rate the technique layer twice.** Every technique record, `affects` edge, maturity judgment, and opportunity score comes from one rater. A second coder should label the seeded sample of {{stat:n_second_coding_edges}} edges by effect, with the coding rule of §8.1 and the sheets `scripts/coding.py` writes, which also ask for the family and admission tests of the sampled mechanics (§2.6, `tasks/second-coding.md`), so that the build reports Cohen's kappa and Krippendorff's alpha overall and per effect; derive edges blind for a sample of mechanics and report recall against the existing ones, starting with the most used unreached mechanics; re-rate maturity, TRL, and horizon for a sample of techniques, including the three TRL mismatches of §7.1; and score at least the top fifteen opportunities. `scripts/panel.py` writes every one of these sheets, and `tasks/second-rating.md` lets one person do them all in a single run; the edges the §8.1 audit relabelled are listed in `report/audits/effect-audit.yaml`, so a coder can test that boundary directly. A second model has filled the same sheets under the records' own operator (§2.6), which shows where the written rules fix a code and where they do not, but not whether a person would agree. Until a person does, the effect counts, the exposure ranking, and the order in §9 are one rater's.{{assert:n_second_coding_runs == 0}}{{assert:n_cross_model_runs == 1}}
7. **Sharpen the predictions.** Have a reader other than the original rater check which predictions are technique tests and which feature tests, and check the baselines and reference classes in `report/predictions.yaml`, which the same rater wrote; have independent raters attach a probability to each before it comes due; and add an undetermined outcome to the vocabulary for predictions that public evidence cannot decide. Amend the {{stat:n_predictions_console_alternative}} criteria whose console clause sets no audience size, and write down why each review bar is what it is.
8. **Check the atlas's own judgments against outside evidence.** Check a random sample of games' core and supporting tags against their cited sources and report an error rate (§2.4); test whether the prior-art searches retrieve shipped titles and mods already known to do a feature, and widen the queries with synonyms where they do not (§9.1); recode the runtime techniques against written tests for replay, cross-machine identity, lockstep, and counterfactual re-simulation (§6.4); and rerun the rating simulations of §5.6 with a shift between raters, mechanics drawn by family, and errors shared across scales.

### 11.2 How to extend this report

The report is generated. To add a game, mechanic, technique, or opportunity, follow `AGENTS.md`; tables, counts, figures, rankings, and this section's prediction list update on the next build. To change an argument, edit the prose in `report/src/`; every dataset number in it is a token, so the text cannot fall out of date with the data.
