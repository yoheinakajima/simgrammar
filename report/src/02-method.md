## 2. Method

### 2.1 Unit of analysis: the mechanic

A **mechanic** here is a rule-system that passes four admission tests (CONTRACT.md, I12). Each test has a procedure; two of them have a threshold the validator enforces, and two are judgments the build cannot check.

- **Nameable.** Designers would recognize it in games other than the one being examined. The name describes the rule rather than one title's term for it, and a mechanic whose maturity is classic or established must be tagged on at least two catalog games (E017); only emerging and experimental mechanics may sit on one, and {{stat:n_mechanics_one_game}} do.
- **Atomic.** It owns one kind of state and one update rule, which its `definition` names. If it splits into two parts that each appear without the other in shipped games, it is two mechanics. This is a judgment made when the mechanic is written.
- **Tunable.** It has at least two levers. The schema requires at least two entries in `design_levers`; every mechanic lists at least {{stat:min_design_levers}}, and the median is {{stat:median_design_levers}}.
- **Removable.** A game could drop it and keep running. This too is a judgment. The build checks only the weaker condition that no mechanic is in every catalog game: the most used, {{stat:most_prevalent_mechanic}}, is in {{stat:most_prevalent_mechanic_share_pct}} percent of them.{{assert:most_prevalent_mechanic_share_pct < 100}}

Interface mechanics pass the atomic test on presentation state. An inspector owns its selected agent and the fields it exposes ([[agent-inspection]]), an alert feed owns its list of active alerts with their severities and lifetimes ([[alerts-feed]]), and an overlay owns which map mode is shown and the color ramp it draws through ([[data-overlays]]); each updates that state from simulation state that other mechanics own, which is the sense in which §4.1 says they own no simulation state of their own.{{assert:field.agent-inspection.family == information-legibility}}{{assert:field.alerts-feed.family == information-legibility}}{{assert:field.data-overlays.family == information-legibility}} Control mechanics pass it on a command channel, state that persists between the player's actions and that agents or machines consume (§1.1). The tests therefore admit presentation, control, and clock mechanics beside the ones that own simulation state.

The tests exclude two common confusions. Dynamics such as "cascading failure" or "death spiral" are outcomes of coupled mechanics, so they appear in mechanics' `dynamics` fields rather than as entities. Genre-level patterns such as "colony management" are combinations, so they appear as game decompositions or opportunities. The result sits between the MDA framework's *mechanics* layer and a designer's pattern language: concrete enough to implement, general enough to recur (§1.1).

Each mechanic belongs to one of {{stat:n_families}} families, assigned by the state it owns rather than the genre it appears in, against the family definitions in `vocab/mechanic_family.yaml`. The rules apply in order, and the first that fits decides:

1. A mechanic whose update rule writes only what the player is shown is information and legibility ([[agent-inspection]]). One that writes the simulation clock or its rate is time and pacing ([[variable-speed]]). One that writes a standing channel from player intent to action is control and automation ([[designation-orders]]).
2. Otherwise the family is the one whose definition names the variable the update rule stores between ticks: [[weather]] is environment, [[labor-market]] is economy. How the player reaches the mechanic does not decide its family; that is the `player_interface` field. [[natural-language-interaction]] takes free text, but the state it owns is a character's interpretation of the utterance and reply, so it is social relations; [[player-legislation]] writes laws, so it is governance.
3. When a rule writes one variable from another, the stored variable decides. [[supply-demand-pricing]] stores prices computed from stocks of goods, so it is economy; [[goods-consumption]] draws down stocks of goods and passes the share of needs met to other mechanics, so it is resources and production.
4. A value held inside one agent is agents and behavior ([[needs-decay]]); a value attached to a pair or group of agents is social relations ([[relationship-values]], [[reputation]]); a count over many agents is population and lineage ([[population-strata]]).
5. Moving goods along a route is logistics ([[conveyor-transport]]) unless a price difference drives the exchange, which makes it economy ([[trade-routes]]).{{assert:field.variable-speed.family == time-pacing}}{{assert:field.designation-orders.family == control-automation}}{{assert:field.natural-language-interaction.family == social-relations}}{{assert:field.player-legislation.family == governance-policy}}{{assert:field.supply-demand-pricing.family == economy-finance}}{{assert:field.goods-consumption.family == resources-production}}{{assert:field.needs-decay.family == agents-behavior}}{{assert:field.relationship-values.family == social-relations}}{{assert:field.reputation.family == social-relations}}{{assert:field.population-strata.family == population-lineage}}{{assert:field.conveyor-transport.family == logistics-networks}}{{assert:field.trade-routes.family == economy-finance}}

These rules were written down after the families were assigned, from the assignments they describe; each family and each admission decision was made by the run that created the mechanic, and no second coder has repeated them, so agreement on both is unmeasured.

### 2.2 Corpus

The game catalog was built to cover every subgenre in the vocabulary, every lineage-defining title from the 1960s onward, recent releases through {{stat:year_max}}, research demonstrations that run as interactive simulations (such as [[generative-agents-smallville]] and [[project-sid]]), and works included for a single mechanic (marked `boundary_case`; {{stat:n_boundary_cases}} such works). The catalog is a purposive sample, not a census: prevalence figures describe this corpus, and the year of a mechanic's earliest catalog game is an upper bound on the year it originated (the mechanic is at least that old), since an earlier game that used it may be missing.

A game's year is the year of its first public release, early access and open betas included, and its mechanics are those of the feature set its sources describe. For a game changed after release, that feature set can include parts added later, so the year can predate some of what the record decomposes; a use note that knows when a feature arrived says so. The records' fields and notes show {{stat:n_games_dating_exposed}} games exposed to this: {{stat:n_games_dating_early_access}} early-access titles (a recorded 1.0 year, or design notes that say early access), {{stat:n_games_dating_persistent_online_world}} persistent online worlds, and {{stat:n_games_dating_later_feature}} games whose use notes date part of a mechanic to a later update, expansion, DLC, or version, some under more than one heading (`dist/analysis/dating-exposed-games.csv`).{{assert:n_games_dating_exposed > 0}} §5.2 recomputes its counts without them.

### 2.3 Schema and scoring

Every categorical field draws from a closed vocabulary (`vocab/`), and every ordinal field names an anchored rubric (`vocab/rubrics.yaml`). Scorers match the anchor text and take the lower anchor when between two. This trades resolution for consistency across contributors: a 3 in legibility means "understood after deliberate attention and the game's info tools" whoever assigned it. The lower-anchor rule makes each score a claim that the mechanic reaches at least that anchor, and the cost is that a score sits below the scorer's best guess wherever the text falls between two anchors. The original scores were assigned by one model rater (claude-opus-5-5) matching the anchor text. Independent second ratings now cover {{stat:n_scores_independently_rated}} scores from {{stat:n_mechanics_independently_rated}} mechanics; fields with ratings store their lower median, which for two ratings is the lower one, so stored values are conservative in the same direction as the anchor rule. §5.6 reports what storing the mean or the upper rating would change.{{assert:n_scores_independently_rated > 0}} Scores remain judgments, and the rubric for each is reproduced in the wiki.

Two scales share a word. A game's `emergence` score (§3) is anchored on what players report about the whole game, up to histories no one could have authored. A mechanic's `emergence_potential` score is anchored on what the mechanic produces "when coupled with others", up to "a primary engine of emergent stories wherever it appears", so a rater judges it from how the mechanic behaves alongside others in the games that use it. It rates a mechanic's typical contribution in context, not a property the mechanic has on its own, and emergence potential in this paper always means the mechanic score.

Relations are typed edges with one owner each (`vocab/edge_types.yaml`). Inverses (which games use a mechanic, which techniques affect it) and all aggregates (prevalence, earliest appearance, clusters, technique exposure, opportunity priority) are computed by the build and never stored, so they cannot drift from the edges they summarize.

### 2.4 Evidence

Each record carries an epistemic status. `asserted` means written from domain knowledge and not yet promoted on the strength of a source; `sourced` means at least one cited source supports its factual fields; `verified` requires a second, independent run; `contested` means sources disagree, and both sides are cited. Techniques must always cite. At this version, {{stat:n_sourced_or_verified}} of the {{stat:n_records}} records are sourced or verified, {{stat:n_contested}} is contested,{{assert:n_contested == 1}} and {{stat:n_asserted}} remain asserted; the asserted ones form a public verification queue (`dist/analysis/verification-queue.csv`). Status and citing are different counts. {{stat:n_records_citing}} records cite at least one source, more than are sourced or verified, because the contested record cites both sides and {{stat:n_asserted_citing}} asserted records already cite a source in a claim but have not been promoted.{{assert:n_records_citing > n_sourced_or_verified}} So every technique is sourced or verified,{{assert:n_technique_asserted == 0}} every game cites at least one source,{{assert:n_game_no_sources == 0}} and {{stat:n_game_sourced_or_verified}} of the {{count:game}} games are sourced or verified; every opportunity is asserted, because an opportunity is an argument with no source to cite.{{assert:n_opportunity_asserted == n_opportunity}}

### 2.5 Production

The dataset was produced by parallel research runs, each recorded in `log/runs/` with its operator, model, method, and the proposals it could not act on. Every run was an AI agent run directed by a human operator: all {{stat:n_runs}} runs in the log name an agent model, {{stat:n_runs_top_model}} of them {{stat:top_run_model}} and the rest other models ({{stat:n_run_models}} models in all), under {{stat:n_run_operators}} operators.{{assert:n_runs_agent == n_runs}}{{assert:n_runs_top_model <= n_runs}} Parallel runs partitioned work by file, not by topic: taxonomy runs analyzed mechanics; catalog runs verified release facts against public sources and decomposed games; technique runs searched the 2019 to 2026 literature and developer announcements. Merge-time runs then edited entities across partitions: the synthesis run added symmetric synergy and tension edges in one pass, without written criteria for either, and a review run added mechanic tags to games after an independent review found widely shared mechanics (pause controls, placement, tech trees) under-tagged, recoded several decompositions, and tightened every prediction. Each cross-partition edit is attributed in the entity's `provenance.reviewed` list. A validator enforcing the rules in CONTRACT.md §5 gated every merge. The same procedure (AGENTS.md) is what a new contributor, human or agent, follows.

The build, drawn in [the figure below](#fig-pipeline), checks three things on every change. It validates every record against the schemas, vocabularies, and contract rules. It fills in every number in the prose from the data, so no count is typed by hand. And it evaluates {{stat:n_report_assertions}} assertions carried by {{stat:n_report_sentences_asserted}} of the paper's {{stat:n_report_sentences}} prose sentences, failing when the data stop supporting the ranking, sign, threshold, grouping, or stored field a sentence states; records carry {{stat:n_record_assertions}} more assertions of the same kind.{{assert:n_report_sentences_asserted < n_report_sentences}} These checks keep the prose consistent with the records. They do not test whether a record is right about a game (sources, quotes, and verification runs address that, §2.4), whether a mechanic was coded correctly, or whether an interpretation is valid: an assertion can confirm that a correlation is negative, not that it means what the sentence says it means. The numbers in the {{stat:n_report_sentences_with_numbers}} sentences that state one agree with the data by construction; the readings the prose gives of them are the authors'. Because {{stat:n_runs_top_model}} of the {{stat:n_runs}} runs used one model, agreement between those runs is not independent evidence; only verification runs, second ratings, and prediction resolutions must come from a different operator and, when both runs are agents, a different model (E035).

### 2.6 Limitations

- **Sampling.** Commercial, English-language, PC-centric titles are over-represented; mobile management games and non-Western simulation traditions are under-represented.
- **Scoring.** Most rubric scores remain judgments by the original model (claude-opus-5-5), with an independently rated subset. They are not measurements of player behavior. Correlations among scores (§5.6) and between a score and the technique graph (§8.4) partly reflect that rater's internal consistency. Each score can carry `ratings` from further raters, each with a run and a rationale; the original score counts as one of them, and the stored value is their lower median (E037). A rater must come from a different operator, and a different model for agents (E035), and must first agree with a calibration set of {{stat:n_calibration_mechanics}} mechanics (E036). The calibration's reference scores are public, so it shows that a rater reads the anchors as the set does, not that the rater scored blind. {{stat:n_scores_independently_rated}} of the {{stat:n_mechanic_scores}} mechanic scores have a second, independent rating so far.
- **The second rater.** One rater has added ratings so far:{{assert:n_rating_runs == 1}} a model (gpt-6.1-sol) under a different operator, in run `2026-10-29-shreyko-antim-rate-scores-19`. By that run's record, the rater first scored the calibration sheet, which gives each calibration mechanic's summary, definition, player experience, and levers with the anchors and no scores, and fixed those scores before they were compared with the reference. It then scored the {{stat:n_mechanics_independently_rated}} mechanics of its task from a packet of their definitions, player experience, levers, failure modes, and dynamics, again without stored scores, earlier ratings, rationales, or provenance. That account is the operator's: the reference scores are public, and nothing in the data shows that the rater did not see them. Two facts the records do establish limit what the agreement shows. Both raters read descriptions written by the original rater in the same runs that assigned its scores, so a judgment carried in that text, such as a failure mode saying players misread a hazard, reaches both; the agreement in §5.6 is therefore an upper bound on what fully independent raters would reach. And the rated mechanics were not sampled: they are the first batch the task generator (`scripts/make_tasks.py`) handed out, the mechanics outside the calibration set taken in alphabetical order of id, and the operator claimed that task, so the agreement may not hold for the rest of the vocabulary. Ratings on a sample stratified by family and score and of about {{stat:n_alpha_sample_max_best}} mechanics (§5.6), from raters who write their own descriptions or score from play, need new raters and are not part of this version.{{assert:n_alpha_sample_max_best > n_mechanics_independently_rated}}
- **The rated mechanics.** The table below sets the families of the {{stat:n_mechanics_independently_rated}} doubly rated mechanics against the vocabulary's and the calibration set's. They come from {{stat:n_rated_families}} of the {{stat:n_live_families}} families. Information legibility supplies {{stat:n_rated_family_information_legibility}} of them ({{stat:pct_rated_family_information_legibility}} percent, against {{stat:pct_family_information_legibility}} percent of the vocabulary), and agents and behavior {{stat:n_rated_family_agents_behavior}} ({{stat:pct_rated_family_agents_behavior}} against {{stat:pct_family_agents_behavior}} percent). Information legibility is one of the two families that §5.6 finds at the floor of emergence potential.{{assert:n_rated_families < n_live_families}}{{assert:pct_rated_family_information_legibility > pct_family_information_legibility}}{{assert:pct_rated_family_agents_behavior > pct_family_agents_behavior}}{{assert:pct_interface_emergence_1 >= 50}} Summed over families, {{stat:pct_family_departure_rated}} percent of the doubly rated mechanics would have to change family for their shares to match the vocabulary's. No sample this small can match the shares of every family, and as many mechanics drawn at random would depart by {{stat:pct_family_departure_random_median}} percent on median, so any such sample departs far; the alphabetical one departs further than a typical random draw, toward the two families above.{{assert:pct_family_departure_rated > pct_family_departure_random_median}} The draw also narrows the range of legibility. The doubly rated mechanics' stored legibility scores sit on {{stat:n_rated_anchors_legibility}} anchors, against {{stat:n_anchors_legibility}} across the vocabulary, and spread {{stat:pct_sd_rated_legibility}} percent as widely (in standard deviation), the narrowest of the scales.{{assert:n_rated_anchors_legibility < n_anchors_legibility}}{{assert:sd_ratio_rated_legibility == sd_ratio_rated_min}} When most ratings share an anchor, chance agreement is high and each disagreement weighs more, so the raters chose the same legibility anchor more often than the same authoring-cost anchor ({{stat:pct_rater_exact_legibility}} against {{stat:pct_rater_exact_authoring_cost}} percent) and still reached a lower alpha ({{stat:alpha_rater_legibility}} against {{stat:alpha_rater_authoring_cost}}).{{assert:pct_rater_exact_legibility > pct_rater_exact_authoring_cost}}{{assert:alpha_rater_legibility < alpha_rater_authoring_cost}} The simulations in §5.6 use each scale's spread over the whole vocabulary instead.

- **Coding.** Families, admission, tags, `affects` edges, effect types, maturity, and opportunity scores were each assigned by the run that created the record, and the technique layer has had no recall audit (§11). For three of these decisions a second coder now has a sample and coding sheets, but no codes have been collected yet, so agreement on all of them is still unmeasured (§2.1, §8.1).{{assert:n_second_coding_runs == 0}} The sample is seeded, stratified by the current codes, and recorded in `report/analysis.yaml`: {{stat:n_second_coding_mechanics}} mechanics from all {{stat:n_second_coding_families}} families, to be coded for family and for the four admission tests; {{stat:n_second_coding_candidates}} proposed mechanics that the vocabulary has not taken up, mixed into the admission sheet so that the tests have something to reject; and {{stat:n_second_coding_edges}} `affects` edges from all {{stat:n_second_coding_effects}} effect types and {{stat:n_second_coding_techniques}} techniques, to be coded for effect.{{assert:n_second_coding_families == n_family_terms}}{{assert:n_second_coding_effects == n_effect_terms}} The sheets (`scripts/coding.py`) give the rules of §2.1 and §8.1 and each item's own description, never its current code. A coder's codes go in `report/coding/` under the run and operator that made them, and the build then reports Cohen's kappa and Krippendorff's alpha for each decision, with bootstrap intervals. It refuses codes from a run with the same operator as any run that created or reviewed a coded record, or with the same model when both are agent runs. Agreement on admission will compare the coder with the dataset's boundary, not with recorded reasons: every admitted mechanic was coded as passing all four tests, and no taxonomy run recorded a decision on the candidates.
- **Decomposition depth.** A game's mechanic list records what is present and meaningful, not a complete specification. Absence of an edge is weak evidence of absence.
- **Recency.** Technique maturity and horizon are judged as of the run date and age quickly; each technique records the sources the judgment rests on.
